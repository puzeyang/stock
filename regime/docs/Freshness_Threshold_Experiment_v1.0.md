## 2. Boundary semantics (fixed before evaluation, per family)

**Corrected per ChatGPT msg 134 item 4** — availability *state* and *reason code* are separate axes, not one overlapping vocabulary. A record has exactly one state and, when informative, exactly one reason.

**States (mutually exclusive, exactly one applies):**

- **CURRENT**: an observation exists and is usable for measurement, whether or not it just arrived exactly on schedule.
- **STALE**: the most recent usable observation is older than its availability deadline plus the allowance `N` — i.e., `N+1` or more missed expected sessions/business days since that observation. An old observation exists; it is aging past tolerance.
- **MISSING**: no prior usable observation exists at all for the required as-of date. Distinct from STALE — there is nothing to age.
- **MISALIGNED**: a observation exists and would otherwise be CURRENT by the count below, but fails the family's `point_in_time_join_rule` (e.g., a same-day lookahead attempt). A join-rule violation, not a freshness violation — already closed under MAN-007-R1, included here only so the full vocabulary is enumerable.

**Reason codes (attached to a state; every state has exactly one applicable code or explicit absence — corrected per ChatGPT msg 136 item 2, which is right that leaving STALE/MISSING/MISALIGNED with no literal code at all contradicts MAN-009's own reason-code assertion and this thread's msg 119-120 agreed minimum vocabulary — missing/stale/late-unavailable/misaligned):**

Machine-readable state→reason mapping (closed vocabulary; no other code is valid):

| State | Allowed reason code(s) | Meaning |
|---|---|---|
| CURRENT | `null` (absence — the on-time case; no reason code applies) | Observation arrived on schedule, no lateness to explain. |
| CURRENT | `SOURCE_LATE_WITHIN_GRACE` | Expected publication deadline passed with no new observation, but the existing one is still within its `N`-session/business-day allowance. Informational, not terminal. **Explicit fail-closed clarification, per ChatGPT's specific question:** this code permits full Condition computation using the existing observation; it does not merely permit retention of a displayed prior state. The allowance `N` exists precisely to define how long a late-but-not-yet-stale observation remains usable for computation, not just for display — if the intent were display-only retention, `N` would be redundant with STALE's own definition. Deliberate design choice, stated explicitly so it cannot be silently narrowed later. |
| STALE | `SOURCE_STALE` | The most recent usable observation is older than its availability deadline plus `N`; `N+1` or more missed expected sessions/business days have elapsed since it. |
| MISSING | `SOURCE_MISSING` | No prior usable observation exists at all for the required as-of date. |
| MISALIGNED | `SOURCE_MISALIGNED` | An observation exists and would otherwise be CURRENT by the count above, but fails the family's `point_in_time_join_rule`. |

`SOURCE_STALE`/`SOURCE_MISSING`/`SOURCE_MISALIGNED` are terminal for freshness-classification purposes in this experiment — their downstream handling (fail-closed unavailability of the dependent Condition/pillar) is already fixed by v5.1 §4.1 and MAN-006/007-R1, not reopened here. This table only formalizes their reason-code identity, which MAN-009's own assertion requires exist and which the prior draft omitted.

**Boundary arithmetic:** an observation is CURRENT through its `point_in_time_join_rule` availability deadline (MAN-007-R1) plus exactly `N` completed expected sessions (XNYS/Cboe) or FRED business days (OAS, applied after the T+1 floor) — inclusive of `N` itself. It becomes STALE immediately after that allowance is exhausted, i.e. at `N+1` missed expected sessions/business days, never at `N`.

## 3. FRED three-way condition split (resolves the cadence confound, msg 124/125)

Every FRED evidence interval (natural or injected) is labeled as exactly one of:

- **(a) Provider non-publication** — FRED itself did not publish a new `BAMLH0A0HYM2` observation for the interval; this is normal cadence behavior for this series, not a pipeline failure. Still relevant to semantic freshness (the observation is aging) but must not be counted as an outage when measuring false-unavailability/outage-frequency claims.
- **(b) Fetch outage** — FRED published, but this pipeline's acquisition missed or lagged behind the publication. This is the only condition that counts as a genuine outage for causal candidate comparison.
- **(c) Calendar closure** — a declared non-business day under `FRED_BUSINESS_DAY`. Not an outage; handled by the calendar, never counted as missing/stale evidence.
- **(indeterminate)** — historical release/arrival evidence cannot distinguish (a) from (b) for a given interval. Excluded from any claim about *observed* outage frequency. Controlled injections (§4) are used for causal (a)-vs-(b) comparison instead of relying on ambiguous historical evidence.

## 4. Deterministic injection registry

### 4.1 Requirements (msg 123 item 3, msg 124 item 3, msg 125 item 4)

Every synthetic injection MUST be pre-selected and registered — with source family, outage length, selection rationale, calendar status, surrounding data completeness, and crisis/trend-stratum membership — **before** any candidate outcome is computed. Injected outage lengths: `{1, 2, 3, 5}` expected sessions/business days, applied to each family separately.

Exclusions (msg 128 leakage-prohibition parity, validation-plan §5.5):
- No injection on a declared holiday/non-business-day (would conflate calendar closure with an outage).
- No injection into a pre-existing natural gap (would conflate two effects into one observation).
- No injection into a date range that was used to *derive* the boundary semantics in §2 (would let the same evidence both invent and confirm the rule).

Balance: injections are stratified across ordinary, crisis, and trend periods per validation-plan §5.1's named-episode taxonomy, so no single regime dominates the evidence.

Holdout: a subset of registered injection dates is set aside, untouched, and excluded from all development-frontier computation. It is unsealed exactly once, after the ceiling is frozen (§6). Section 1.1 requires at least two independent holdout entries per family so the confirmatory rate/duration claim does not rest on a single held-out event, and the full `{1,2,3,5}` outage-length grid plus all three regime strata apply to the holdout split exactly as they do to development (msg 136 item 1, msg 138 item 1) — the holdout split is not a lighter-coverage subset of the requirement, it is the same requirement applied to a disjoint, sealed set of dates.

**Clarification on eligibility scope (msg 138 item 5):** synthetic injections simulate a *fetch outage* — this pipeline's acquisition failing to retrieve an already-published observation — not a claim about what the historical arrival/publication timestamp of that observation actually was. Verifying that an injection date is eligible therefore requires only: (a) the date is not a declared holiday/closure, (b) the underlying source has a real, present row for that date in the pinned local snapshot (i.e., the observation was genuinely published and is not itself part of a natural gap), and (c) it is not adjacent to a pre-existing natural gap. It does NOT require reconstructing FRED's actual historical publication or vendor-arrival timestamp for that observation — that information is not preserved in the current snapshot and is not needed to simulate a fetch outage, since the injection asserts "our side failed to retrieve this," not "the provider published this at time X." The three-way (a)/(b)/(c)/indeterminate split in §3 governs *natural* evidence, where the true publication/fetch distinction is genuinely unknown and must be labeled indeterminate rather than guessed; it does not apply to injected evidence, where the outage is definitionally condition (b) by construction. Do not treat live-FRED historical-arrival classification as a blocking requirement for injection eligibility — it isn't one.

No entry may be added, edited, or have its `split` value changed after the development-frontier computation begins (§5). Corrections are new, separately timestamped entries with a superseded-by cross-reference, following this whole validation ledger's own append-only discipline.

## 5. Metrics (development frontier only)

Per candidate, per family, computed only over `split: development` evidence (natural + injected):

- False-unavailability rate (fraction of true-current observations the candidate would flag stale/unavailable).
- Stale-as-current exposure duration (sessions a truly-stale observation is treated as current before the candidate catches it).
- Affected Condition/regime bars (count of measurement outputs touched by a freshness misclassification).
- Delayed crisis detection (lag introduced into CRISIS domain confirmation, if any, by a stale input).
- Spurious state transitions attributable to a freshness misclassification.
- Turnover impact and recovery time.

Portfolio return is not a metric in this experiment (validation-plan §6.3, msg 123 item 4 — measurement/operational-integrity metrics only; return-based selection is explicitly prohibited here, not merely deprioritized).

## 6. Two-stage decision procedure (msg 127, refined msg 128–129)

**Stage 1 — development frontier (authorized only once this document leaves DRAFT status per §7; this section describes what Stage 1 will consist of when that gate is met):**
Compute §5 metrics for every candidate in each family's grid, using development-split evidence only. Produce one frontier artifact per family: candidates plotted/tabulated by false-unavailability rate vs. stale-as-current exposure, with candidate identity visible (e.g., "XNYS N=1") — identity is not hidden, per msg 128 item 1, since the ceiling decision is about tradeoff shape, not candidate selection.

**Stage 1 output, content-addressed and timestamped:** the exact frontier table/chart shown to the human, per family.

**Stage 2 — human sets the ceiling (requires human judgment; not authorized by this document alone):**
The human is shown the Stage-1 frontier artifacts (development evidence only — no holdout metrics, no portfolio outcomes) and sets:
- A hard maximum stale-as-current exposure ceiling, with explicit units (sessions).
- The rationale for that number.

This decision, the presented artifact's hash, the numeric ceiling, the units, who set it, and the timestamp are recorded in the registry (msg 129). This is a risk-preference elicitation, not a candidate-selection step — the actual winning candidate is a mechanical consequence of applying the frozen rule next, not a choice made here.

**Stage 3 — frozen rule, one-time holdout application:**
Once the ceiling is frozen: among candidates in each family whose Stage-1 stale-as-current exposure is at or below the ceiling, select the one minimizing false-unavailability rate (lexicographic selection per msg 125's recommendation, adopted). Apply that frozen, family-specific rule once to the untouched holdout injection set. Record a separate, explicitly timestamped "holdout-unseal" event and hash the resulting report.

If no candidate in a family satisfies the ceiling, that family reports a **no-selection outcome** — the ceiling itself is not silently loosened to force a winner (msg 125).

**Post-unseal integrity rule (msg 129):** any change to the ceiling after unsealing invalidates confirmatory status for that family and requires a newly registered, distinct holdout set. No silent relabeling of a post-hoc adjustment as if it were confirmatory.
